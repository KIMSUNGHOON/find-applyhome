# 청약홈 스캔 결과 공유 캐시 — 설계

작성일: 2026-07-24
선행 스펙: [2026-07-24-vercel-deploy-design.md](2026-07-24-vercel-deploy-design.md)

## 1. 배경

현재 웹 앱은 사용자가 단지를 조회할 때마다 브라우저가 모든 동·호를 다시 순회한다.
같은 단지를 여러 방문자가 연달아 조회해도 이전 결과를 재사용하지 않으므로 응답이 늦고,
청약홈에도 동일한 요청이 반복된다.

Vercel Functions의 로컬 파일시스템은 영구적이거나 인스턴스 간 공유되지 않으므로 일반 SQLite
파일은 공유 저장소로 사용할 수 없다. 모든 함수와 방문자가 함께 쓰는 외부 저장소가 필요하다.

## 2. 목표와 비목표

### 목표

- 모든 방문자가 단지별 최신 스캔 결과를 공유한다.
- 저장된 결과를 먼저 표시하고 필요한 항목만 청약홈에서 다시 확인한다.
- 여러 방문자가 동시에 같은 항목을 재확인하지 않도록 분산 잠금을 건다.
- 캐시 장애가 기존 직접 조회 기능을 중단시키지 않게 한다.
- Upstash Redis Free 플랜의 저장 공간과 명령 수를 아껴 쓴다.

### 비목표

- 날짜별 변경 이력과 과거 스냅샷 보관
- 사용자 계정, 사용자별 데이터, 즐겨찾기
- 크론 작업이나 상시 백그라운드 수집
- 통계·검색을 위한 관계형 데이터 모델
- 검색 결과(`/api/search`) 캐싱
- 저장소·개발자·출처를 표시하는 footer 변경 — 별도 후속 설계에서 다룬다

갱신은 방문자가 단지를 조회할 때 발생한다. 방문이 없는 단지를 주기적으로 스캔하지 않는다.

## 3. 저장소 선택

Upstash Redis를 사용한다.

- Vercel Marketplace가 프로젝트에 접속 URL과 토큰을 환경변수로 주입한다.
- HTTPS REST API라 Python 서버리스 함수에서 연결 풀 없이 사용할 수 있다.
- Redis Hash로 호실 하나만 덮어쓸 수 있다.
- `SET NX EX` 기반 잠금과 TTL을 지원한다.
- Python 표준 라이브러리로 호출할 수 있어 새 런타임 의존성이 필요 없다.

검토했지만 선택하지 않은 대안은 다음과 같다.

| 대안 | 선택하지 않은 이유 |
|---|---|
| 일반 SQLite | Vercel 함수에 모든 인스턴스가 공유하는 영구 파일시스템이 없다 |
| Vercel Blob | 일부 호실 갱신도 전체 객체 재기록이 필요하고 동시 쓰기 충돌을 조정하기 어렵다 |
| Vercel Runtime Cache | 단순 객체 캐시에는 맞지만 Hash 부분 갱신과 분산 잠금에 필요한 Redis 연산이 없다 |
| Postgres·Turso | 변경 이력과 복잡한 질의에는 적합하지만 최신 스냅샷 캐시에는 스키마와 운영 부담이 크다 |

환경변수 이름은 Upstash 기본값을 그대로 사용한다.

```text
UPSTASH_REDIS_REST_URL
UPSTASH_REDIS_REST_TOKEN
```

두 값은 Python API에서만 읽는다. HTML, JavaScript, API 응답, 로그에 토큰을 포함하지 않는다.

## 4. 논리 구조와 Redis 키

단지 하나를 Redis Hash 하나로 저장한다.

```text
scan:v1:{houseManageNo}:{pblancNo}
├─ _dongs           현재 동 목록 + checked_at
├─ t:{dongSn}       해당 동의 호 목록·grid + checked_at
├─ _supply          공급유형 정보 + checked_at
├─ u:{dong}:{ho}    해당 호의 최신 상태·필드 + checked_at
└─ u:102:301        다음 호실 필드
```

승인된 논리 필드 `_topology`는 실제 Redis에서는 `_dongs`와 `t:{dongSn}`으로 나눈다.
브라우저가 동별 호 목록을 동시에 조회하므로 동별 필드를 독립적으로 기록해야 서로의 결과를
덮어쓰지 않는다. `/api/cache`는 이 필드들을 합쳐 하나의 topology로 반환한다.

각 필드 값은 JSON 문자열이다. 시간은 UTC Unix 초 단위 정수 `checked_at`으로 저장한다.

```json
{
  "dong": "101",
  "ho": "201",
  "status": "info",
  "fields": {"주택형": "084.8422A"},
  "checked_at": 1784871000
}
```

호실 상태는 기존의 `info`, `empty`, `error` 세 가지를 유지한다. `error`는 브라우저가 보낸
값이 아니라 Python API가 직접 청약홈 호출 실패를 확인했을 때만 저장한다. 과거 값은 쌓지 않고
동일 필드를 최신 값으로 덮어쓴다. Redis 키와 필드에 들어가는 외부 식별자는 길이를 제한하고
percent-encoding하며, 원래 동·호 값은 JSON 안에 보존한다.

처음 조회한 호실이 실패하면 `error`를 저장한다. 이미 `info` 또는 `empty`인 호실의 재확인만
실패한 경우에는 유효한 상태와 필드를 유지하고 `last_error_at`, `last_error`를 덧붙인다. 자동
재시도는 마지막 실패로부터 24시간 뒤에 하되 사용자의 `실패 항목 재시도`는 이 대기 시간을
무시한다. 일시적인 청약홈 장애가 기존 정상 결과를 지우지 않게 하기 위한 규칙이다.

## 5. 보존 기간과 완전성

단지 Hash의 TTL은 마지막 읽기 또는 쓰기부터 90일이다. `/api/cache` 읽기와 각 write-through
쓰기는 데이터 연산과 `EXPIRE`를 한 REST pipeline으로 묶는다. 90일 동안 조회되지 않은 단지는
자동 삭제된다.

topology가 완전하다는 조건은 다음과 같다.

1. `_dongs`가 존재한다.
2. 현재 `_dongs`에 들어 있는 모든 동에 `t:{dongSn}`이 존재한다.
3. 각 `t:{dongSn}.checked_at`이 `_dongs.checked_at` 이상이다.

3번 조건 때문에 새 동 목록을 저장한 뒤 아직 호 목록을 다 받지 못한 중간 상태를 과거 topology와
혼동하지 않는다. 완전한 topology에서 기대되는 `(dong, ho)` 중 `u:{dong}:{ho}`가 모두 있으면
스냅샷도 완전하다. 이전 topology에만 존재하던 고아 호실 필드는 응답에서 제외하며 `/api/cache`
읽기 시 정리한다.

공급유형 정보는 부가 정보이므로 `_supply` 누락이나 `null`은 스냅샷 완전성을 막지 않는다.

## 6. 최신성 정책

서버의 현재 시각을 기준으로 판정한다. 브라우저 시각은 신뢰하지 않는다.

| 조건 | 동작 |
|---|---|
| 캐시 없음 | 기존 전체 스캔 |
| 일부 topology 또는 호실 누락 | 저장된 결과를 표시하고 누락분만 조회 |
| `empty` 또는 `error`가 24시간 경과 | 해당 호실만 재확인 |
| 동 목록이 비어 있거나 `_supply`가 `null`인 채 24시간 경과 | 해당 자료만 재확인 |
| 완전한 topology가 7일 경과 | 동·호 구조와 현재 전체 호실을 재확인 |
| 사용자가 전체 새로고침 요청 | 동·호 구조, 공급유형, 현재 전체 호실을 재확인 |

`info` 호실은 topology 전체 갱신 전까지 재사용하며 최대 7일마다 다시 확인한다. `empty`는 등록
지연 뒤 `info`로 바뀔 가능성이 있어 24시간마다 확인한다. `error`는 자동으로 24시간 뒤 확인하되,
기존 `실패 항목 재시도` 동작으로 즉시 다시 조회할 수도 있다.

`checked_at`은 보수적으로 현재 topology와 현재 호실들의 가장 오래된 확인 시각을 사용한다.
화면에서는 브라우저의 로컬 시간대로 변환해
`저장된 결과 · 마지막 확인 2026-07-24 14:30` 형식으로 표시한다.

## 7. API

### 7.1 `GET /api/cache`

쿼리:

```text
hm={houseManageNo}&pb={pblancNo}
```

응답 예시:

```json
{
  "cache": "stale",
  "complete": true,
  "checked_at": 1784871000,
  "meta": {
    "total": 1,
    "dongs": [{"name": "101", "hos": ["201"], "grid": {}}],
    "supply": []
  },
  "units": [{
    "dong": "101",
    "ho": "201",
    "status": "empty",
    "fields": {},
    "checked_at": 1784871000
  }],
  "refresh": {
    "topology": false,
    "supply": false,
    "all_units": false,
    "units": [{"dong": "101", "ho": "201"}]
  }
}
```

`units`에는 저장된 현재 호실 전체가 들어간다.

`cache` 값은 다음과 같다.

| 값 | 의미 |
|---|---|
| `disabled` | 환경변수 누락 또는 이 요청에서 Redis를 사용할 수 없음 |
| `miss` | 단지 Hash가 없음 |
| `partial` | topology나 기대 호실 일부가 없음 |
| `fresh` | 추가 조회가 필요 없음 |
| `stale` | 저장 결과를 쓸 수 있지만 정책에 따라 일부 또는 전체 재확인 필요 |

`refresh`는 브라우저가 수행할 작업을 서버 시각으로 계산한 결과다. 정책을 JavaScript에도 복제하지
않는다. 손상되거나 파싱할 수 없는 Redis 필드는 무시하고 `partial`로 처리한다.
`disabled`와 `miss`는 `meta: null`, `units: []`, `refresh.topology: true`를 반환해 기존 전체
스캔으로 연결한다.

### 7.2 기존 API의 write-through

기존 공개 API 형태를 유지하고 Python API가 직접 수행한 청약홈 조회 결과를 바로 저장한다.
`/api/unit`의 최초 조회 실패는 `error`로 저장하지만, 다른 API의 `502` 응답은 저장하지 않는다.

| API | 저장 필드 |
|---|---|
| `/api/dongs` | `_dongs` |
| `/api/hos` | `t:{dongSn}` |
| `/api/pblanc` | `_supply` |
| `/api/unit` | `u:{dong}:{ho}` |

캐시 쓰기가 실패해도 청약홈에서 받은 원래 API 응답은 성공으로 반환한다. 브라우저가 캐시 내용을
POST하는 API는 만들지 않는다. 따라서 방문자가 임의의 호실 결과를 공유 캐시에 주입할 수 없다.

### 7.3 전체 새로고침 승인

`GET /api/cache?hm=2025000439&pb=2025000439&refresh=full`은 현재 스냅샷과 함께 단지별
10분 cooldown 획득 결과를 반환한다. cooldown은 Redis의 원자적 `SET NX EX 600`으로 만든다.

```json
{"full_refresh": {"allowed": false, "retry_after": 412}}
```

일반 `/api/cache` 읽기에서 7일 경과를 발견한 경우에도 서버가 같은 cooldown 획득을 시도하고
`full_refresh`를 응답에 포함한다. 자동 7일 전체 갱신과 수동 전체 새로고침은 같은 cooldown을
사용한다. 승인되지 않은 브라우저는 기존 스냅샷을 유지하고 `다른 방문자가 업데이트 중` 또는
남은 대기 시간을 표시한다. Redis가 비활성화된 경우에는 cooldown 없이 직접 조회를 허용한다.

## 8. 동시 요청 제어

호실 재확인 전에 다음 잠금을 원자적으로 획득한다.

```text
lock:scan:v1:{houseManageNo}:{pblancNo}:{dong}:{ho}
SET key {ownerToken} NX EX 30
```

- 잠금 소유자만 청약홈을 호출하고 결과를 Hash에 쓴다.
- 기존 호실 값이 있는 비소유자는 그 값을 `refreshing: true`와 함께 받는다.
- 기존 값도 없는 비소유자는 `202`와 `status: refreshing`을 받는다.
- 소유자는 임의 토큰 비교 후에만 잠금을 해제한다. 함수가 중단되면 30초 TTL이 해제 역할을 한다.
- Redis 장애 시 잠금을 건너뛰고 기존 직접 조회로 진행한다.

비소유 브라우저는 `/api/unit`을 다시 호출해 중복 갱신을 시작하지 않는다. 대신 0.5초, 1초,
2초 뒤 `/api/cache`를 최대 세 번 다시 읽어 더 최신 `checked_at` 결과로 교체한다. 세 번 뒤에도
새 값이 없으면 기존 값은 유지하고, 값 자체가 없으면 그 호실만 화면상 `error`로 표시한다. 이
화면상 오류를 브라우저가 Redis에 쓰지는 않는다.

잠금은 중복 호출을 줄이는 최적화이며 데이터 응답의 필수 조건이 아니다.

## 9. 브라우저 흐름

사용자가 단지를 선택하고 조회를 시작하면 다음 순서로 동작한다.

1. `/api/cache`를 호출한다.
2. `meta`와 `units`가 있으면 즉시 기존 `state.meta`, `state.units`에 넣고 화면을 그린다.
3. `fresh`이면 종료한다.
4. `miss`이면 현재의 전체 브라우저 스캔을 실행한다.
5. `partial`이면 topology와 호실 중 누락된 부분만 채운다.
6. `stale`이면 저장 결과를 유지한 채 `refresh`가 지정한 작업을 백그라운드에서 실행한다.
7. 새 응답이 올 때마다 화면의 해당 호실과 요약을 교체한다.

진행 문구는 저장 결과와 신규 조회를 구분한다.

```text
저장된 결과 224 / 242 · 업데이트 6 / 18
```

중단 버튼은 브라우저가 아직 시작하지 않은 작업만 취소한다. 이미 Vercel 함수에 도착한 최대 3개
요청은 완료되어 Redis에 저장될 수 있다. 사용자가 탭을 닫아도 완료된 일부 결과는 남고, 다음
방문자가 누락분을 이어서 채운다.

CSV는 캐시 결과와 이번에 갱신한 결과가 합쳐진 `state.units`로 생성한다. CSV 생성 시점에 별도
네트워크 요청을 하지 않는다.

## 10. 화면 변경

- 최초 조회 버튼은 캐시 읽기부터 시작한다.
- 결과 상단에 `저장된 결과`, 마지막 확인 시각, `업데이트 중`, `일부 데이터만 저장됨`을 표시한다.
- 결과가 있는 상태에서 `전체 새로고침` 버튼을 제공한다.
- 전체 새로고침 cooldown 중이면 남은 시간을 안내하고 기존 결과를 유지한다.
- 캐시 장애 자체는 사용자 작업을 막는 오류로 표시하지 않는다. 직접 조회 진행 상태만 보여준다.
- 기존 판정 주의문, 그리드, 상세 보기, 실패 재시도, CSV 형식은 유지한다.

## 11. 실패 처리

| 실패 | 동작 |
|---|---|
| Upstash 환경변수 없음 | `cache: disabled`; 기존 직접 스캔 |
| Redis 읽기 실패·시간초과 | 이번 요청에서 cache miss처럼 처리; 직접 스캔 |
| Redis 쓰기 실패 | 청약홈 원본 응답은 그대로 반환; 다음 방문 때 다시 채움 |
| Redis 필드 JSON 손상 | 해당 필드를 누락으로 간주하고 재조회 |
| 잠금 소유 함수 중단 | 30초 뒤 잠금 자동 만료 |
| 청약홈 개별 호실 실패 | `error` 저장·표시; 다른 호실 계속 진행 |
| 브라우저 중단·종료 | 완료된 결과만 유지; 다음 방문자가 재개 |

Redis REST 요청 타임아웃은 2초로 한다. 전송 실패가 발생한 Vercel warm instance는 60초 동안
캐시 호출을 생략하는 메모리 회로 차단기를 사용한다. 오류 메시지에는 URL의 호스트 외에 토큰이나
요청 인증 헤더를 포함하지 않는다.

## 12. 모듈 경계

```text
api/_cache.py
  - Upstash REST transport
  - Redis 명령·pipeline
  - 키와 필드 이름 생성
  - JSON 직렬화·역직렬화
  - TTL과 잠금
  - 완전성·최신성 판정

api/cache.py
  - Vercel GET 진입점
  - 쿼리 파싱과 JSON 응답

api/_lib.py
  - 기존 청약홈 엔드포인트 로직
  - 성공 결과의 write-through 호출
  - 캐시 실패와 원본 API 성공의 분리

public/index.html
  - 캐시 우선 렌더링
  - refresh 작업 대기열
  - 상태·버튼·CSV 통합
```

`api/_cache.py`는 네트워크 전송 함수를 주입할 수 있게 해 실제 Upstash 없이 테스트한다.
캐시 정책은 이 모듈에만 두고 브라우저는 `refresh` 지시를 실행한다.

## 13. 비용과 명령 수 제어

- 단지 읽기는 `HGETALL`과 `EXPIRE`를 한 pipeline 요청으로 묶는다.
- 쓰기는 해당 필드의 `HSET`과 `EXPIRE`만 수행한다.
- 브라우저는 캐시가 fresh이면 호실별 API를 호출하지 않는다.
- 스냅샷은 한 단지당 Hash 하나이고 과거 이력을 만들지 않는다.
- 90일 미사용 TTL로 장기 미사용 단지를 제거한다.
- 전체 새로고침 10분 cooldown과 호실 잠금으로 중복 명령과 청약홈 요청을 줄인다.

무료 플랜 한도를 코드 상수로 가정하지 않는다. 한도 변경이나 초과로 Redis가 실패해도 fail-open
동작으로 직접 조회 기능을 유지한다.

## 14. 테스트

### Python 단위 테스트

- Redis 키·필드 생성과 입력 검증
- Hash 직렬화·역직렬화
- 완전·부분·손상 스냅샷 조립
- `miss`, `partial`, `fresh`, `stale`, `disabled` 판정
- `empty`·`error` 24시간 및 topology 7일 경계
- 90일 TTL pipeline
- 호실 잠금 획득·경합·만료와 전체 새로고침 cooldown
- 각 기존 API의 write-through 성공과 캐시 쓰기 실패 무시
- Redis 읽기 실패 시 직접 조회 전환
- 기존 정상 호실 재확인 실패 시 값 보존과 24시간 재시도 대기
- Redis 장애 뒤 60초 회로 차단기
- 토큰이 오류와 응답에 노출되지 않음

실제 Upstash 대신 명령과 응답을 기록하는 가짜 transport를 사용한다. 기존 파싱 fixture와 테스트는
그대로 유지한다.

### 프런트엔드 검증

- 캐시 결과가 신규 스캔 전에 렌더링됨
- fresh에서 추가 호실 요청이 없음
- partial에서 누락 호실만 요청함
- stale에서 지정된 `empty`·`error`만 교체함
- 전체 갱신, cooldown, 중단, 동시성 3 유지
- 캐시와 신규 결과가 합쳐진 CSV의 BOM·escaping 유지

### 배포 확인

- Vercel 프로젝트에 두 Upstash 환경변수가 연결되었는지 확인
- 재배포 후 첫 방문은 캐시를 채우고 두 번째 방문은 같은 결과를 즉시 받는지 확인
- 서로 다른 브라우저에서 동일 스냅샷이 보이는지 확인
- 환경변수를 제거한 Preview 배포에서 기존 직접 스캔이 동작하는지 확인

## 15. 배포와 운영

Upstash Free 데이터베이스는 Vercel 프로젝트에 이미 설치되어 있다. 통합이 생성한 환경변수를
Production과 필요한 Preview 환경에 연결한 뒤 재배포해야 함수가 값을 읽는다.

README에는 다음 내용을 추가한다.

- Vercel Marketplace에서 Upstash Redis 연결 방법
- 필요한 환경변수 이름
- 토큰을 저장소와 브라우저에 넣지 말라는 주의
- 환경변수가 없을 때 캐시 없이 동작한다는 설명
- 24시간·7일·90일 정책과 전체 새로고침 cooldown

키 스키마가 호환되지 않게 바뀌면 `scan:v2`처럼 버전을 올린다. 이전 키는 별도 마이그레이션 없이
기존 TTL로 만료시킨다.
