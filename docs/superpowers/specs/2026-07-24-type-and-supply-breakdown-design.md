# 타입·공급유형 구분 보기 — 설계

작성일: 2026-07-24
선행 스펙: [2026-07-24-applyhome-vacancy-scanner-design.md](2026-07-24-applyhome-vacancy-scanner-design.md)

## 1. 배경

기존 스캐너는 세대를 `정보있음 / 정보없음 / 조회실패`로만 구분한다.
사용자는 여기에 두 가지 축을 더 원한다.

- **주택형(타입)별 구분** — 84A, 84B, 84C 같은 타입 단위로 보기
- **공급유형(특별/일반) 구분**

또한 화면이 세로로만 길어져 동이 많은 단지에서 스크롤이 과도하다는 지적이 있었다.

## 2. 검증된 사실 (2026-07-24 실측)

설계의 근거다. 모두 상봉 센트럴 아이파크(`2025000439`) 242세대 스캔 결과와 청약홈 공고를 대조해 확인했다.

### 2.1 스캔 대상은 이미 일반분양 세대 전체다

| | 세대수 |
|---|---|
| 청약홈 공고 「공급규모」 | 242 |
| `selectHoList.do` 가 돌려준 호수 합계 | 242 |

정확히 일치한다. 즉 **호 목록에 조합원분·임대 물량은 애초에 들어 있지 않다.**
격자의 빈칸은 청약홈에 등록되지 않은 호수이며, 일반분양 대상이 아닌 세대로 볼 수 있다.
미계약 추정은 이미 특별공급·일반공급 세대 안에서만 이루어지고 있다.

### 2.2 라인과 타입은 1:1로 대응하며, 유추가 정확하다

호수 끝 두 자리(라인)가 같으면 주택형이 같다. 10개 라인 전부 예외가 없었다.

미계약 18세대의 타입을 라인으로 채워 넣고 공고와 대조한 결과가 완전히 일치했다.

| 타입 | 공고 (일반/특별/계) | 스캔 세대수 | 미계약 추정 |
|---|---|---|---|
| 084.8422A | 22 / 23 / 45 | 45 | 2 |
| 084.7662B | 23 / 26 / 49 | 49 | 4 |
| 084.6747C | 23 / 28 / 51 | 51 | 6 |
| 084.7184D | 23 / 26 / 49 | 49 | 2 |
| 084.9194E | 22 / 26 / 48 | 48 | 4 |
| 합계 | 113 / 129 / **242** | **242** | 18 |

**다만 이것은 한 단지에서 확인한 규칙이다.** 다른 단지에서 깨질 수 있으므로 4절의 교차 검증을 둔다.

### 2.3 공급유형은 세대의 속성이 아니다

같은 라인 안에서도 층마다 특별공급과 일반공급이 섞인다. 10개 라인 전부 혼재했다.

청약홈의 `공급유형`은 **그 세대에 당첨된 사람이 어느 유형으로 청약했는지**를 기록한 값이기 때문이다.
세대에 미리 배정된 딱지가 아니다.

따라서 **미계약 세대에는 공급유형이 존재하지 않는다.** 실측 18건 모두 빈 값이었고, 라인으로 유추할 수도 없다.
세대 단위 특별/일반 표기는 계약이 확인된 세대에 한해서만 가능하다.

### 2.4 공고 상세 API

`GET /ai/aia/selectAPTLttotPblancDetail.do?houseManageNo=<hm>&pblancNo=<pb>` — 인증 없이 열린다.

페이지에는 `<caption>` 이 달린 테이블이 6개 있고, 그중 두 개가 주택형을 담는다.

| caption | 내용 | 사용 |
|---|---|---|
| `입주자모집공고 공급대상` | 타입별 일반/특별/계 세대수 | **이것을 쓴다** |
| `입주자모집공고 특별공급 공급대상` | 특별공급 세부(다자녀·신혼 등) 분해 | 쓰지 않는다 |

캡션이 **완전히 일치**하는 테이블만 고른다. 부분 문자열로 찾으면 특별공급 테이블까지 걸린다.

행 구조는 이렇다.

```
행2: ['민영', '084.8422A', '116.9496', '22', '23', '45', '2025000439(01)']
행3: [        '084.7662B', '117.9958', '23', '26', '49', '2025000439(02)']
...
행7: ['계', '113', '129', '242', '']
```

첫 행에만 주택구분(`민영`/`국민`)이 rowspan 으로 붙고, 마지막에 합계 행이 온다.
그래서 위치 인덱스로 읽지 않고 **주택형 패턴(`\d{2,4}\.\d{2,6}`)이 나온 셀을 기준점**으로 삼아
`[i]=주택형, [i+1]=공급면적, [i+2]=일반, [i+3]=특별, [i+4]=계` 로 읽는다.
합계 행에는 주택형 패턴이 없으므로 자동으로 걸러진다.

장위 푸르지오 마크원(`2026000275`, 18개 타입 1032세대)에서도 같은 구조를 확인했다.

## 3. 목표와 비목표

### 목표

- 공고에서 타입별 `일반 / 특별 / 계` 세대수를 가져와 타입별 현황표를 보여준다.
- 격자에서 타입과 공급유형을 세대 단위로 식별할 수 있게 한다.
- 격자 빈칸의 의미를 화면에 밝힌다.
- 동 블록을 화면 가로 폭에 맞춰 배치한다.

### 비목표 (YAGNI)

- 타입 필터(선택한 타입만 표시) — 격자 헤더 표기만으로 구분이 되므로 넣지 않는다
- 특별공급 세부 유형(다자녀·신혼·생애최초 등) 분해
- 오피스텔·도시형·민간임대 공고 대응 (엔드포인트가 다르다. 5절의 실패 처리로 흡수한다)

## 4. 기능 상세

### 4.1 타입 축약 표기

청약홈 원본은 `084.8422A` 처럼 길다. 화면에서는 **`84A`** 로 줄인다.

규칙: **앞자리 0을 버린 정수부** + **소수점 이하 숫자열 뒤에 남는 문자**.
정규식 `^0*(\d+)\.\d+(.*)$` 로 잡아 `group(1) + group(2)` 를 이어 붙인다.

| 원본 | 축약 |
|---|---|
| `084.8422A` | `84A` |
| `039.7700A` | `39A` |
| `046.8700` | `46` |
| `059.9800A1` | `59A1` |
| `114.2100` | `114` |

상세 패널과 CSV에는 원본을 그대로 남긴다. 축약은 표시 전용이다.

### 4.1.1 면적 두 가지를 혼동하지 않는다

주택형 문자열과 공고 테이블은 **서로 다른 면적**을 담고 있다. 화면에서 섞으면 안 된다.

| 값 | 출처 | 상봉 84A 예시 |
|---|---|---|
| **전용면적** | 주택형 문자열의 숫자부 | `084.8422A` → 84.8422㎡ |
| **공급면적** (주거전용+주거공용) | 공고 테이블의 `주택공급면적` 칸 | 116.9496㎡ |

전용면적은 주택형에서 뽑아 쓴다 — `^0*(\d+\.\d+)` 로 잡고 앞자리 0을 버린다
(`084.8422A` → `84.8422`). 공고 조회가 실패해도 전용면적은 항상 표시할 수 있다.

### 4.2 타입별 현황표

격자 위에 놓는다. 이번 작업의 본체다.

```
타입별 현황                                     공고 기준 · 상봉 센트럴 아이파크
 타입    전용        공급        공고(일반/특별)   미계약 추정    비율
 84A    84.84㎡    116.95㎡     45 (22 / 23)          2         4.4%
 84B    84.77㎡    118.00㎡     49 (23 / 26)          4         8.2%
 84C    84.67㎡    117.15㎡     51 (23 / 28)          6        11.8%
 84D    84.72㎡    119.48㎡     49 (23 / 26)          2         4.1%
 84E    84.92㎡    118.29㎡     48 (22 / 26)          4         8.3%
 합계                           242 (113 / 129)       18         7.4%
```

- `전용` — 주택형에서 뽑은 전용면적. 소수점 둘째 자리까지 반올림해 표시한다
- `공급` — 공고의 `주택공급면적`. 같은 규칙으로 표시한다
- `공고(일반/특별)` — 공고 상세에서 가져온 값
- `미계약 추정` — 스캔 결과 `empty` 세대를 타입별로 집계. 미계약 세대의 타입은 라인으로 채운다
- `비율` — 미계약 ÷ 공고 계. 공고 조회 실패 시에는 미계약 ÷ 스캔 세대수

정렬은 전용면적 오름차순, 같으면 타입 코드 순이다 (`39A, 39B, 46, 51A, …, 114`).

### 4.3 격자 표기

배경색을 **네 가지**로 나눈다. 상태 세 가지 중 `정보있음` 을 공급유형에 따라 둘로 가른다.

| 칸 | 색 | 뜻 |
|---|---|---|
| 파랑 | `#5c7cfa` | 정보있음 · 특별공급 |
| 회색 | `#adb5bd` | 정보있음 · 일반공급 |
| 주황 | `#e8590c` | 정보없음 (미계약·부적격 추정) |
| 빨강 | `#c92a2a` | 조회실패 |

**주황이 가장 눈에 띄어야 한다.** 이 도구를 쓰는 이유가 미계약 세대를 찾는 것이기 때문이다.
파랑은 주황의 보색이라 서로 간섭하지 않고, 적록색맹에서도 파랑과 회색은 구분된다.

공급유형을 읽지 못한 세대는 `.cell.info` 기본값인 회색으로 떨어진다.
청약홈이 예상 밖의 문자열을 주더라도 칸이 비어 보이지 않는다.

**글자(`특`/`일`)는 색과 겹치지만 그대로 둔다.** 색맹 대응이자, 화면을 캡처해 공유할 때 색만으로는 설명이 되지 않기 때문이다.

```
101동 · 119세대
        01     02     03     04     05
       84A    84B    84C    84D    84E
 28F   [일]   [일]   [특]   [일]   [특]
 23F   [일]   [ ●]   [ ●]   [일]   [특]
 20F   [특]   [특]   [일]   [ ●]   [일]
```

- 헤더 2행 — 라인 번호 아래에 축약 타입
- 셀 배경 — 위 4색 표대로
- 셀 글자 — `특` 또는 `일`. 미계약·실패 세대는 공급유형이 없으므로 글자 없음
- 셀 크기 26px → **30px** (한 글자를 넣기 위해). 라인이 10개여도 300px 이라 문제없다

한 라인에 두 타입이 섞이는 단지가 있을 수 있다. 그 경우 **헤더에 `혼합`** 이라 쓰고,
각 세대의 실제 타입은 셀 툴팁(`title`)에서 보여준다.

### 4.4 범례

빈칸의 의미를 명시한다. 지금은 설명이 없어 오해를 부른다.

```
■ 특별공급 92   ■ 일반공급 132   ● 정보없음 18
빈칸 = 청약홈 미등록 (조합원·임대 등 일반분양 외 물량)
색과 글자(특·일)는 그 세대 당첨자의 청약 유형입니다
```

공급유형을 읽지 못한 세대가 있으면 `유형미상 N` 항목이 함께 나온다. 없으면 표시하지 않는다.

### 4.5 공고 ↔ 스캔 교차 검증

타입별로 공고 세대수와 **스캔 세대수**(= 그 타입으로 집계된 세대 수. 미계약 세대는 라인으로 채운 값)를
대조해, 어긋나면 현황표 위에 경고를 띄운다.

> ⚠ 84C 타입: 공고 51세대 / 스캔 49세대 — 라인과 타입의 대응이 단순하지 않은 단지일 수 있어
> 타입별 집계가 정확하지 않을 수 있습니다.

2.2절의 라인 유추가 통하지 않는 단지를 사용자가 즉시 알 수 있게 하는 안전장치다.
일치하면 아무것도 표시하지 않는다.

### 4.6 미계약 세대 상세

미계약 세대를 클릭했을 때 타입 정보를 함께 보여준다.

```
101동 305호 — 정보없음 (미계약·부적격 추정)
84E · 전용 84.92㎡ · 공고 48세대 (일반 22 / 특별 26)
```

세대 단위 공급유형은 존재하지 않으므로, 그 타입의 공고 배정 세대수를 참고로 붙인다.
공고 조회에 실패했으면 `84E · 전용 84.92㎡` 까지만 표시한다.

### 4.7 정보없음 목록과 CSV

목록에 `타입` 컬럼을 추가한다. 컬럼은 `동 / 호 / 타입 / 주택형(참고)` 이다.

CSV 헤더에도 `타입` 을 추가한다. 위치는 `호` 와 `판정` 사이다.

```
동,호,타입,판정,주택형,공급유형,공고일,당첨자 발표일,계약체결일,입주예정,전매제한,분양금액(만원)
```

`empty` 세대의 `타입` 은 라인에서 채우고, `주택형` 원본 칸은 지금처럼 빈 채로 둔다
(청약홈이 주지 않은 값을 지어내지 않는다).

### 4.8 레이아웃 — 화면 폭 활용

현재 `body` 에 `max-width: 1100px` 가 걸려 있어 넓은 화면에서 좌우가 크게 비고,
동 블록이 세로로만 쌓인다. 장위처럼 동이 23개인 단지에서는 스크롤이 과도하다.

```css
body   { max-width: none; padding: 16px 20px; }
#grids { display: flex; flex-wrap: wrap; gap: 20px 26px; align-items: flex-start; }
.dong  { margin: 0; }
```

동 하나의 폭은 라인 수에 비례한다(5라인 기준 약 210px). 1800px 화면이면 가로로 7~8개가 들어간다.
층수가 제각각이라 높이가 다르므로 `align-items: flex-start` 로 위쪽을 맞춘다.

함께 손봐야 할 두 가지가 있다.

- 범례가 `#grids` 안에 들어가는데, flex 로 바꾸면 마지막 동 **옆에** 붙는다. `flex-basis: 100%` 로 줄바꿈시킨다.
- 정보없음 목록 표가 `width: 100%` 라 초광폭 화면에서 양끝으로 벌어진다. `max-width: 820px` 로 묶는다.

## 5. 공고 조회 실패 시

오피스텔·도시형·민간임대는 공고 엔드포인트가 다르다(`selectOtherLttotPblancListView.do` 계열).
조회나 파싱이 실패하면 다음과 같이 동작한다.

- 스캔은 그대로 진행한다. 공고는 부가 정보이므로 스캔을 막지 않는다
- 현황표는 **스캔 결과만으로** 만든다 (타입 / 스캔 세대수 / 미계약 / 비율). `공고(일반/특별)` 칸은 `-`
- 표 옆에 `공고 대조 불가` 라고 표시한다
- 교차 검증(4.5)은 건너뛴다

| `static/index.html` | 현황표·격자 헤더·셀 글자·범례·교차검증·레이아웃 |

`SupplyType` 데이터클래스를 새로 둔다.

```python
@dataclass(frozen=True)
class SupplyType:
    house_type: str   # "084.8422A" 원본
    area: str         # "116.9496" 공급면적
    general: int      # 일반공급 세대수
    special: int      # 특별공급 세대수
    total: int        # 계
```

`meta` 이벤트에 실리는 형태는 다음과 같다.

```json
{
  "total": 242,
  "dongs": [{"name": "101", "hos": ["303", ...], "grid": {...}}],
  "supply": [{"type": "084.8422A", "short": "84A", "area": "116.9496",
              "general": 22, "special": 23, "total": 45}]
}
```

`supply` 는 공고 조회에 실패하면 `null` 이다.

라인↔타입 대응은 스캔이 끝나야 알 수 있으므로(정보있음 세대의 주택형에서 역산),
현황표와 격자 헤더는 프론트가 `unit` 이벤트를 받아가며 채운다.

### 6.1 타입 축약이 양쪽에 필요하다

축약·전용면적 추출은 **Python 과 JavaScript 양쪽에 각각 구현한다.**

- Python — 공고에서 받은 `supply` 배열에 `short` 를 채워 보낼 때 (`grid.short_type`)
- JavaScript — 스캔 결과의 주택형과 라인 유추 타입을 화면에 그릴 때 (`shortType`, `netArea`)

프론트가 라인에서 역산한 타입은 서버를 거치지 않으므로 서버 계산만으로는 덮을 수 없다.
중복이지만 불가피하다. 두 구현이 어긋나면 격자 헤더와 현황표의 타입 이름이 달라지므로,
**4.1절의 정규식을 양쪽에 그대로 사용하고 같은 입력 5종(`084.8422A`, `039.7700A`, `046.8700`,
`059.9800A1`, `114.2100`)으로 각각 테스트한다.**
